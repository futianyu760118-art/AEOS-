# ADR-2026-011：基线代际拆分为「V1.0 受控基线」与「V7.2.2 执行候选」

- 状态：Proposed（2026-11-21，待 M00 治理 Owner 与 PMO 确认）
- 日期：2026-11-21
- 影响系统：M00 GOV（治理与基线）、全系统（执行口径引用方）
- 相关：ADR-2026-001（manifest 视为锁文件）、`docs/BASELINE_MANIFEST.md`

## Context

2026-09-22 的 `docs/BASELINE_MANIFEST.md` 登记了 4 份项目级最小基线（执行方案 V1.0、
执行手册 V1.0、进度表 V1.0、Data Foundation V0.2），属于 **2026-09 代口径**：

- 执行方案：12 个月首期（2026-09-01～2027-08-31）、P0–P7 阶段、M00–M12 + M03A；
- 执行手册：19 条宪法 C01–C19、G0–G6 放行条件；
- 进度表：5 表、27 项检查（绑定 19 条宪法与 12 个月任务）；
- Data Foundation V0.2（2026-09-07）。

2026-10-14 起项目实际执行口径已切到 **V7.2.2 资料包**：9 个月 / 36 周（建议起始
2026-10-19）、G0–G8、M00–M14（新增 M13 Hub、M14 NOMI）、命名冻结候选 V1.3，
但该资料包整体仍是「候选 / 待评审签批」，执行前评审总方案尚未签批，
P0-03/04/05、POMS V2.2、M14 NOMI 来源仍缺文件/来源/版本/SHA-256。

同时，4 份基线原件自 2026-09 以来 3 份缺失、1 份损坏；2026-11-21 已从用户传输包
（`AEOS_Source_Archive_2026-11-21.zip`）按清单 SHA-256 找回 4/4 受控字节并回填
`docs/`。仓库因此出现「基线是 12 个月代、registry 是 15 系统代、文档层大量引用
36 周口径」的混代状态。

若不把代际关系写清楚，会产生两种错误：

1. 认为 `check_baseline.py --strict` 通过就代表「基线口径与当前执行一致」——它只
   校验字节，不校验代际；
2. 把未签批的 V7.2.2 候选直接替换进 `docs/` 并改 `check_baseline.py` 期望值，使
   「候选」变成「受控」，重演 V1.0 先入库、签批长期不来的问题。

## Decision

1. **V1.0 四份文件继续作为项目级受控基线**，以原始字节回填 `docs/`，不改名、不重签、
   不重算清单；`BASELINE_MANIFEST.md` 增加「代际」与「现行状态」两列，标明
   `2026-09 / V1.0` 与「已回填（2026-11-21）」。
2. **V7.2.2 资料包是当前执行候选，不是受控基线**。在以下条件全部满足前，不得替换
   `BASELINE_MANIFEST` 条目、不得改 `check_baseline.py` 期望值：
   - `AEOS_V7.2.2_执行前评审总方案` 签批；
   - P0-03 Data Ownership、P0-04 Object ID、P0-05 Contract Pack 补齐文件/版本/SHA；
   - POMS V2.2 缺文件/来源/版本/SHA 补齐；
   - M14 NOMI 正式来源补齐；
   - 命名冻结候选 V1.3 由 M00/M01/M02/M12/M13/M14 Owner 与 PMO 签批。
3. **19 条宪法 C01–C19 继续适用**；团队执行手册 V7.2.2 是执行层补充（角色、36 周
   节奏、M13/M14 分工），不替代宪法条款。
4. **基线升级 V1.1（36 周口径）单独走一次变更**：新建 ADR + 重新发布清单 + 重算
   SHA-256 + Owner 签批；建议内容为执行方案 V1.1（36 周）、团队执行手册 V7.2.2、
   进度表 V1.1（36 周台账 + G0–G8 检查项）、Data Foundation V0.2（保留不变）。
5. **门禁语义声明**：`check_baseline.py --strict` 通过 = 字节与清单一致；不代表签批
   完成，也不代表与 V7.2.2 执行口径一致。代际一致性由本 ADR 与清单列记录。
6. 清理失效重建路径：删除 `staging/base64/` 半成品与 `.github/workflows/rebuild-aeos-docs.yml`
   （该流程依赖 `staging/READY` 与 4 组分片，前置条件从未补齐，且仓库托管 Gitee、
   GitHub Actions 不会执行）。

## Alternatives

- **A. 直接用 V7.2.2 替换 4 份基线并改清单**：口径统一，但 V7.2.2 未签批、来源缺口
  未补，等于把候选当受控；且会与已找回的 V1.0 受控字节形成双份受控件。否决。
- **B. 只回填 V1.0，不记录代际**：门禁转绿但混代问题留在暗处，下一轮仍会有人用
  「基线已通过」推断「执行口径已对齐」。否决。
- **C. 维持现状，等 V7.2.2 签批后一次性切换**：门禁继续红、基线继续缺失，期间所有
  「受控基线成立」的声明都不成立。否决。
- **D（采纳）：双轨记录 + 分阶段升级**——先回填 V1.0 并明确代际，再在 V7.2.2 满足
  签批与来源条件后发布 V1.1。

## Consequences

- 好处：门禁可立即转绿且语义明确；历史受控字节可复现；V7.2.2 与 V1.0 的关系有据可
  查，避免第三套口径。
- 代价：升级 V1.1 前，仓库同时存在两代文档（`docs/` 为 V1.0 受控，`docs/AEOS_各子系统
  最新方案_20261014_V7.2.2同步更新/` 为 V7.2.2 候选），评审者必须先看「代际」列
  再引用。
- 对 CI：`check_baseline.py` 的期望值保持 V1.0 不变；若后续升级 V1.1，需同步改
  期望值并留下 commit SHA 作为重建证据。

## Owner

M00 GOV（治理与基线）。Proposed：2026-11-21；生效：待 M00 治理 Owner 与 PMO 确认

## Rollback

还原 `docs/BASELINE_MANIFEST.md` 的两列与 ADR 文件即可；`docs/` 下 4 份二进制不被
本 ADR 修改，无需回滚字节；删除 ADR 后按原「缺失/损坏」状态恢复红线。
